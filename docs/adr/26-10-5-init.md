# CLI interface

**Context:** We need an interface for developers to produce metrics for problems.
**Decision:** Create a CLI to run problems on specific hardware with a dataset.
**Reasons:** A CLI provides an easy interface where we can specify the problem type, dataset, and hardware for execution.

# Engine decorator

**Context:** We want to be able to use different engines to run problems. Either fully remote, local, or hybrid.
**Decision:** Use engines declared through a decorator and registered in the EngineRegistry.
**Reasons:** Users can now decide which engine to use and create their own.

# Algorithm decorator

**Context:** We want to have a collection of problem implementations and allow users to create new ones.
**Decision:** Use algorithms declared through a decorator and registered in the AlgorithmRegistry.
**Reasons:** We can now define different algorithms and store them in a collection using a simple Python decorator.

# Module

**Context:** We want to ease the creation of algorithms and reuse blocks.
**Decision:** Create modules that can separate parts of algorithms.
**Reasons:** We can now create algorithms without needing to reimplement all the steps.

# Module decorator

**Context:** We want to register modules somewhere and retrieve them easily.
**Decision:** Create a module decorator that registers both core modules and the user's local modules.
**Reasons:** Modules are now stored in a registry, and users can create new ones with a simple Python decorator.
